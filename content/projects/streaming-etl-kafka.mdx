## Approach

Batch pipelines answer yesterday's questions. When data arrives continuously — device telemetry, user events, sensor readings — the pipeline needs a buffer between the thing producing data and the thing storing it.

- **Produce.** An Airflow DAG pulls a record from an external API (randomuser.me stands in for any real feed), reshapes it into a flat row with a UUID key, and publishes it to the `users_created` Kafka topic. Fetching, formatting and publishing are three separate tasks, so each one can be retried by itself.
- **Buffer.** Kafka, running in KRaft mode, sits between producer and consumer. The consumer can crash, redeploy or lag without the producer noticing and without losing the stream.
- **Consume.** A standalone Python consumer in its own consumer group writes each message into a PostgreSQL table, creating the table on startup if it is missing.
- **Observe and export.** Grafana reads the table directly, so throughput and contents are visible as the data arrives. A second daily DAG exports the table to MinIO (S3-compatible) as a dated CSV.

## Data quality & testing

- **Idempotent sink.** The target table has a primary key, and every insert uses `ON CONFLICT (id) DO NOTHING`. Replaying the topic or re-running the DAG cannot create duplicate rows.
- **Retries.** Every Airflow task inherits `retries: 5` with a 5-minute delay, so a flaky upstream API heals itself instead of paging someone.
- **Failure isolation.** The consumer commits per message and rolls back on any error, so one malformed record cannot poison the rows around it.
- **Replay from the start.** `auto.offset.reset: earliest` means a brand-new consumer group reads the topic from the beginning instead of silently skipping history.
- **Honest gap.** There is no automated test suite yet — that's the first item below.
