## Approach

Raw e-commerce data — orders, items, customers, payments, reviews, geolocation — is only useful once it is typed, de-duplicated and modelled. The [Olist Brazilian e-commerce dataset](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) is a realistic stand-in: nine files with the usual problems.

- **Bronze — land it raw.** An Airflow task lists every CSV in the MinIO bucket and streams each into its own bronze table in 20,000-row chunks with pandas. Memory stays flat even on the ~1M-row geolocation file. Nothing is cleaned here; bronze is the audit trail.
- **Silver — clean and type it.** A PL/pgSQL procedure reloads silver from bronze: lifecycle text columns become real timestamps, city names are standardised, and category and payment labels are normalised.
- **Gold — model it.** A snowflake schema built as views: `fact_orders` at order-item grain, plus customer, product and seller dimensions with surrogate keys. Because gold is views, it always reflects the latest silver load.
- **Orchestrate it.** One seven-task DAG: check for new files → register procedures → bronze → load → silver → gold → archive. It runs daily and can be restarted from any task.

## Data quality & testing

- **Guard against empty runs.** A `ShortCircuitOperator` skips the whole run when the landing prefix has no CSVs, so an empty bucket can never wipe the warehouse.
- **No double loads.** Files are moved to `archive/` only after a successful load, so the same file is never ingested twice.
- **Idempotent layers.** Bronze is dropped and recreated each run; silver is truncated and reloaded. Rerunning a day produces the same tables.
- **Grain checks.** Geolocation has many rows per zip prefix, so it is averaged to one point per prefix before joining. Joining it raw would duplicate customers and sellers.
- **No double counting.** Payments are recorded per order, so they are allocated across order items by item value. `SUM(payment_value)` on the fact table matches order totals. The 775 orders with no items are documented and excluded.
- **Profiling queries.** The SQL checks in `tests/` cover duplicate keys, row counts, the 27 expected states, and timestamp ordering (approval before purchase, answer before review). They are run by hand today; automating them is the first item below.
